SENTINEL JUNCTION - IDS AND IPS LAB
CLICK-BY-CLICK STUDENT GUIDE (NO ANSWERS)
============================================================

PURPOSE OF THIS DOCUMENT
------------------------
Use this guide if you are unsure what to click, what to read, or what the lab expects.
It explains every step without revealing the answers. You are allowed to use all in-lab hints.
There is no timer. Most learners should allow about 90 to 120 minutes.

The lab is a safe browser simulation. It does not scan, block, or connect to any real system.
All public-looking IP addresses use fictional documentation ranges.


WHAT YOU WILL LEARN
-------------------
By the end of the lab, you should be able to explain:

1. What an Intrusion Detection System (IDS) does.
2. What an Intrusion Prevention System (IPS) does.
3. Why an IDS normally sees a copy of traffic.
4. Why an IPS must be inline to prevent traffic.
5. How signature, behaviour and policy detections differ.
6. Why an alert is a starting point, not automatic proof of an attack.
7. How source, destination, protocol, port, time, action and rule fields help an analyst.
8. What true positive, false positive, false negative and true negative mean.
9. How to classify a basic alert using asset, user, time, baseline and approval context.
10. Why safe tuning narrows a rule instead of simply turning it off.
11. How to write a factual hand-off that separates known facts from unknowns.


BEFORE YOU START
----------------
1. Open index.html in a modern browser, or open the GitHub Pages link provided by your instructor.
2. Use a normal browser window. Do not use private/incognito mode if you want progress to remain saved.
3. Keep this text file open in a separate window if you need assistance.
4. Do not open the instructor answer key unless your instructor tells you to do so.

Important words:

- ALERTED: detection logic matched and a record was created.
- ALLOWED: the traffic was permitted to continue.
- BLOCKED or DROPPED: an inline control prevented that recorded connection.
- CONTEXT: additional facts that help explain what the alert means.
- BASELINE: a measured picture of what is normally expected.
- FALSE POSITIVE: harmless or approved activity caused an alert.
- FALSE NEGATIVE: harmful activity happened but no alert was created.

PART 6 - HOW TO SOLVE EVERY ALERT CASE
--------------------------------------
There are 16 guided alert cases. Use this exact routine every time.

1. Scroll to “Alert investigation queue.”
2. Click the first alert row. The detail drawer opens.
3. Read the RAW ALERT RECORD from top to bottom.
4. Answer these questions on paper or in your head:
   - When did it happen?
   - What sensor produced it?
   - What is the source?
   - What is the destination or target pattern?
   - Which service or protocol is involved?
   - Does the action say ALERTED, ALLOWED, BLOCKED or DROPPED?
   - Which rule matched?
5. Read every bullet in the CONTEXT DRAWER.
6. Compare the raw alert with the context. Do not use severity alone.
7. Under CLASSIFICATION, choose one:
   - Likely expected or authorised.
   - Suspicious - investigate further.
   - High-confidence malicious.
8. Under RESPONSE, choose one:
   - Allow or close with clear notes.
   - Collect evidence and monitor.
   - Block or contain and escalate.
9. Under STRONGEST EVIDENCE, choose the option that combines the most relevant independent facts.
10. Click “Check all three decisions.”
11. The feedback identifies which decision categories are correct and which need review.
12. If needed, click “Open guided hint.”
13. Change only the categories that need review.
14. Click “Check all three decisions” again.
15. When resolved, the row gains a green border and a RESOLVED label.
16. Click the row to close it.
17. Open the next case.

Questions to ask whenever you feel stuck:

- Is this source asset supposed to perform this activity?
- Is there a change, exercise or maintenance ticket?
- Does the event fall inside the approved time window?
- Is the observed value actually unusual for this asset's baseline?
- Do multiple independent sources support the same conclusion?
- Does the record say ALERTED or BLOCKED?
- What fact is still missing?


PART 7 - SAFE RULE TUNING
-------------------------
1. Scroll to “Safe rule tuning lab.”
2. Read the warning at the top.
3. For tuning case 1, read the problem and all proposed changes.
4. Prefer a change that keeps useful detection while making it more specific.
5. Click “Review change.”
6. Read the result.
7. If incorrect, ask whether your change is too broad, permanent or untested.
8. Retry until the card gains a green border.
9. Repeat for all five tuning cases.

Safe tuning normally uses one or more of these ideas:

- A narrow source exception.
- A documented schedule.
- An asset role.
- A measured baseline.
- A reviewed expiration date.
- A detect-only pilot before prevention.
- Regression tests for allowed and forbidden examples.

TROUBLESHOOTING
---------------
Problem: A Check button says to answer every row.
Solution: Look for a select box still showing “Choose an answer.”

Problem: An alert case will not complete.
Solution: Read the feedback. It names the categories to review. Open the hint and compare all context facts.

Problem: My progress disappeared.
Solution: Use the same browser and lab address. Private browsing, cleared site data, or a different device will not share local progress.

Problem: The animation is not moving.
Solution: Your device may use “Reduce motion.” The lesson still works; read the labels and explanations.

Problem: The certificate remains locked.
Solution: Check the top progress display. It must show 32 / 32 activities. Click “Resume saved progress” to reach the first unfinished activity.

Problem: I want to start again.
Solution: Click “Reset lab” at the top and confirm. This permanently clears this lab's saved browser progress.
